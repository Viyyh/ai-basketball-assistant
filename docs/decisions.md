# 决策记录（ADR）

为什么记这个：这个项目的风险不是"写不出来"，而是"写出来但数字是错的，而且没人发现"。每一条决定都记下当时否掉的方案和否掉的原因 —— 半年后回看，能分清哪些是深思熟虑，哪些只是当时没空。

格式：背景 → 决定 → 后果。**只增不改**；推翻旧决定时新开一条并注明 supersedes。

---

## ADR-001 · demo 作为参考资产，不作为地基

**背景**：`basketball-ai/` 是收到的 F 轨前端 demo（14,475 行，20 页，1020 项测试全绿）。但它的 PRD 明确写着"本产品是数据采集与可视化工具，不是分析工具"，非目标里有"不追求逐人身份识别"。而实际目标是要做 NBA2K 式的球员系统性分析。

**决定**：新仓库 + **搬运三样资产**（报告契约、参数层、设计 tokens），不 fork、不继承其余代码。

**否掉的方案**：
- 全量继承：目标不同，数据模型（事件流 vs 回合流+阵容+属性）不匹配，WXML 绑定微信平台。
- 全新重写：参数层里"同一 6.20m 出手点，U12 判 3 分、成人判 2 分"这类领域知识重写一遍大概率出错，PoC 已验证 U12 误用成人半径会漏判 80%。

**后果**：demo 留在 `reference/` 只读快照里，作为交互参考和测试基线；主产品路径只依赖 `contracts/`、`packages/params`、`packages/design-tokens`。

## ADR-002 · PRD v1.0 冻结，v1.1 用增量文档表达

**背景**：PRD v1.0（861 行）写得相当扎实，但它与"球员分析"目标有五处正面冲突：1.1 性质、1.5 非目标、1.2 用户范围、6.1 不做 ReID/数据分析层、6.3 篮板助攻抢断不做估测、4.3 实体缺 lineup/possession/rating。

**决定**：不修改 `PRD.md`（它记录的是"教练端 v1"的原意，改了会丢失决策轨迹）。新增 `docs/scope-v1.1.md` 只写**增量**，PRD 未提及的沿用原文。

**后果**：读范围要 PRD + scope-v1.1 两份。凡冲突处，scope-v1.1 优先，并在文档里标注对应 PRD 条目号。第二版（球员分析）再单开 v2。

## ADR-003 · 阵营归属不做 AI 推断，交给教练补录

**背景**：单机位一帧里两队都在。最初想用球衣颜色聚类分阵营 —— 业余比赛常见两队都穿深色、或有队员穿错色，误判率 20% 以上，而且是**静默错误**：报告上"我方三分 7/15"混进了对手的出手，教练看不出来。

**决定**：契约加 `team_side`(OURS/OPPONENT/UNKNOWN)，默认 UNKNOWN，只能由教练补录确定。补录动作是零成本的：选我方球员 → 自动 OURS；点"不是我方" → OPPONENT；点"看不清" → UNKNOWN。AI 侧不写任何颜色逻辑。

**后果**：
- 报告拆我方/对方两栏，UNKNOWN 计入 warnings，绝不并入我方。
- 代价是教练每场多花一点补录时间，换来每个数字都可追溯到一次人工确认。
- 若将来 AI 分阵营准确率真能做到 >95%，再考虑自动化，但那需要独立验证集，不是拍脑袋。

## ADR-004 · 进攻方向按节记录，展示层可翻转

**背景**：全场两个篮筐，上下半场换边。原契约没有 `attacking_basket`，mock 数据把 34 个投篮全撒在左半场 —— 真实比赛会出现两个镜像簇，底角/翼侧/弧顶的分区统计会算错。

**决定**：`periods[].attacking_basket`(LEFT/RIGHT/UNKNOWN)，新建活动时教练选"上半场我方进攻方向"，其余节按规则推导（下半场反向）。报告页提供"翻转"开关，**只影响展示**，不改数据。

**后果**：热图默认单框显示（避免两个镜像簇造成的误读），可选全场。缺该字段时显示"进攻方向未确认"横幅而不是画一条可能错的线。

## ADR-005 · 误检用软删除，不物理删除

**背景**：AI 查全率目标 85%，意味着 15% 的出手会漏掉 —— 教练没法修。同时也会误检（把传球判成出手）。

**决定**：事件加 `source`(AI/COACH) 与 `status`(ACTIVE/EXCLUDED)。教练可以"补一次出手"（source=COACH）和"这不是投篮"（status=EXCLUDED，需填 `exclude_reason`）。EXCLUDED 事件保留在数据里，可撤销，不进任何统计。

**后果**：
- 能被重算校验：`team_stats` 必须等于 ACTIVE 事件重算的结果（见 contracts/validate.mjs R7），手填数字会被抓出来。
- 排除原因可积累成 AI 误判的类型分布，是后续调模型的真实标签。

## ADR-006 · 号码即身份（v0 不做跨镜头 ReID）

**背景**：NBA2K 式分析依赖逐人识别。单机位 1080p、看台视角、业余球衣没有姓名条，跨镜头 ReID 在第一版没有成立条件。

**决定**：v0 用"球衣号码 = 队内唯一身份"，按 `player_id` 聚合。号码与姓名的绑定在球队页维护（号码重复时阻止保存）。不承诺跨场次身份延续。

**后果**：这是**已知的天花板**，不是遗漏。真正的逐人跟踪（同场次内跨帧 ID 稳定）是下一个里程碑的生死假设，需要先用真实素材做可行性验证，再决定要不要投入。

## ADR-007 · 评分分档，不做 0-99

**背景**：0-99 看起来专业，但在样本量 3 次出手时是假精确，教练一眼就会不信。NBA2K 的评分是设计出来的，我们的评分必须能从视频里算出来。

**决定**：v0 只做三维（FINISHING 终结 / PERIMETER 中远投 / INVOLVEMENT 参与度），等级 A/B/C/D，外加 `INSUFFICIENT`（样本不足，**明确不是最低档**）。每个维度带 `sample_size`、`make_rate`、`explain_zh`；`rating_rules: "v0"` 版本化，调阈值必须升版本，保证历史数据可回算。

**后果**：第一批球员卡上会大量出现 INSUFFICIENT —— 这是诚实的代价。不做传球/防守/篮板评分，因为那些数据第一版采不到。

## ADR-008 · 契约校验器零依赖，自己写

**背景**：契约是 AI / 后端 / 前端三方共同依赖的东西。若用 ajv，新克隆的仓库要先 `npm i` 才能校验；而 Python 侧还要另找一套，两套实现迟早不一致。

**决定**：`contracts/validate.mjs` 自己实现 JSON Schema 子集（const/enum/type/required/properties/additionalProperties/items/长度与数值边界），加上 `checkSemantics()` 覆盖 10 条跨字段规则。只用 node 内置模块。

**后果**：
- 新增 schema 关键字要同步改校验器（有测试兜底）。
- 语义规则是"数字对不对"的唯一防线：R7 要求统计可由事件重算，R8 要求 coverage 与事件对得上 —— 这两条能抓住大部分静默错误。
- Python 侧暂时复用同一份 JSON 契约，语义校验在 CI 里跑 node 版（见 `README.md`）。

## ADR-009 · 补齐"从相册导入"

**背景**：原 demo 唯一的视频入口是 `wx.createCameraContext().startRecord()`，40 分钟约 5GB，没有 `maxDuration`、没有相册导入。教练的真实情况是：有人用手机拍、有人用相机拍、有人现场录完才有空处理。

**决定**：`wx.chooseMedia`（单文件 ≤2GB）作为一等入口，复用上传页；录制从"唯一入口"降为"可选入口"。契约 `video.source` 区分 CAMERA/ALBUM。

**后果**：相册视频的时长/分辨率/旋转不可控，pipeline 必须做实际校验（而不是假设）。相机长录（切后台、发热、中断）仍未真机验证，是 R2 风险。

## ADR-010 · 数据完整度统一由 coverage 出数

**背景**：报告上写"基于 3 场"，若前端自己数、后端自己算、导出再算一遍，三处迟早不一致。

**决定**：`coverage`(events_total/events_attributed/events_excluded/events_side_unknown) 由 pipeline 产出，前端只读不数。所有"基于 N/M"的标注都从这里取。R8 校验它与事件数量一致。

**后果**：新增统计口径时先扩 coverage，再改前端文案。

## ADR-011 · 三分线统一用 FIBA 成人标准 6.75 m（supersedes PRD 9.5 的 5.80 m 假设）

**背景**：原 demo 与 PRD 9.5 按年龄段给青少年场地 5.80 m（标注"假设值待核实"），成人 6.75 m，3x3 单独一套纯弧线。这套分档从未被教练确认过，却已经被 1020 项测试固化成期望值 —— 一旦实际比赛用成人线，整个人群的三分判定会系统性偏移，而且**不会报错**：报告照样生成，只是"三分 7/15"里混着二分。

**决定**（2026-10-21，产品负责人确认）：所有年龄段统一 **6.75 m + 底角直线段 6.60 m**（FIBA 成人标准）。原 5.80 m 假设作废。

几何形态不再按赛制特判，改为由「半径 + 场地半宽」推导：

```
底角直线段存在  ⟺  radius > 6.60 m  AND  court.y_half > 6.60 m
否则退化为 PURE_ARC（纯弧线）
```

于是 5v5/4v4 全场（半宽 7.5）自然得到"弧线 + 底角"，3x3（15×11，半宽 5.5）自然退化为纯弧线 —— 不需要在代码里写 `if format == '3V3'`。3x3 用纯弧线的原因是场地窄得放不下底角直线段，而不是"3x3 规则特殊"。

> ⚠️ **本段关于 3x3 的前提已被 ADR-014 更正**：3x3 场地实为 15 m 宽 × 11 m 长，半宽 7.5 m，几何同样是「弧线 + 底角」。推导规则不变，仅 3x3 那条结论作废。

交接点 `junction = sqrt(6.75² − 6.60²) ≈ 1.4149 m`，加底线距 1.575 m 得 **2.99 m**，与 FIBA 标准场地一致（`packages/params/tests/test_params.py` 有断言守护）。

**后果**：
- 已知点 6.20 m 现在只是两分（旧 demo 判三分），有专门的回归用例。
- 若某个联赛确实打小球（5.80 / 6.00 / 6.25），在新建活动时传 `three_point_radius_m` 覆盖，几何自动退化并在 `unverified` 里提示；**不改表**——改表会让所有历史报告一起变口径。
- PRD 9.5 那一行保留原文（文档冻结），在本仓库以本 ADR 为准。

## ADR-012 · 参数层只保留 Python 实现

**背景**：旧 demo 里参数表同时存在于 Python（PoC）与 JS（`miniprogram/utils/params.js` + `paramsMirror.js`），靠人工对齐。这种双实现短期看是"前后端各取所需"，长期看必然漂移 —— 其中一边改了半径，另一边在等下一次同步。

**决定**：`packages/params` 是唯一实现，只提供 Python。前端不再解析赛制/年龄段，也不自己算三分线：球场底图、判定参数一律由后端返回的 `params` 段驱动（`CourtGeometry.svg_params()` 就是为此导出的）。

**后果**：
- 前端在断网时无法自行计算分值 —— 这是可接受的：报告本来就是离线产物，渲染时参数已经在报告里。
- 新增赛制只改 Python 一处；JS 侧只消费。

## ADR-013 · mock pipeline 产出物必须过真实契约校验

**背景**：mock 数据最容易变成"看起来像那么回事"的假数据：坐标随手写、分值手填、统计对不上，前端照着它开发，等真实 pipeline 接上时发现字段全部对不上。

**决定**：`services/pipeline` 的 mock **不手写 JSON**。它走真实的 `resolve()` → `CourtGeometry.judge()` → 统计重算，并且测试里通过子进程调用 `contracts/bin/validate-report.mjs` 做跨语言校验。`contracts/fixtures/sample-report.json` 就是它的产出。

**后果**：
- 改动参数层（比如半径）会导致 fixture 变化，这是**特性**：契约样例永远跟着真实逻辑走。
- mock 的"假"只剩一处：事件本身是脚本化的。坐标、分值、标签、统计都是真算的。
- 3x3 等变体下 mock 会自动过滤掉不成立的事件（不识别快攻、坐标落在场外），而不是硬塞。

## ADR-014 · 3x3 场地尺寸更正（supersedes ADR-011 的几何结论）

**背景**：ADR-011 断言"3x3 场地 15×11、半宽 5.5 m，所以自然退化为纯弧线"。对照 FIBA 规则与官方场地说明后确认 **3x3 场地是 15 m 宽 × 11 m 长（宽 > 长）**，原实现把长短边写反了。

**决定**：
- `FIBA_3X3_LENGTH_M = 11.0`、`FIBA_3X3_WIDTH_M = 15.0`（此前为 15.0 / 11.0）。
- 3x3 半宽因此是 7.5 m > 6.60 m，几何判定为 `ARC_AND_CORNERS`，与 5v5 相同 —— 3x3 的"2 分线"仍是"弧线 + 底角直线段"，只是分值换成 1/2 分。
- ADR-011 的推导规则本身（由半径与半宽决定几何形态）不变，只有"3x3 是窄场地"这个**前提**被推翻。

**后果**：
- 修复前，3x3 底角两分会被判成一分的区域（|y| 在 6.60–7.5 之间、x 在 1.4 附近）会静默算错。这类错误不会抛异常，只会在报告里显示成一串"近投(1分)"。
- 存量数据：仓库尚无真实报告，无历史数据需回算。
- 教训：**场地尺寸这类"常识"必须落在有出处的常量上**，而不是凭记忆；已补 `docs/fiba-conformance.md` 逐条对照，并加了方向性断言测试。

## ADR-015 · 场地标线由参数层导出，前端不写死

**背景**：球场底图上要画限制区、罚球线、中圈、无撞人半圆。这些数字如果散落在前端 SVG 代码里，改一次规则就会漏一处。

**决定**：新增 `CourtMarks`（罚球线 5.80 / 限制区 4.90×5.80 / 中圈 1.80 / 无撞人半圆 1.30 / 掷球入界线 8.325 / 线宽 0.05），随 `ActivityParams` 走；`svg_params()` 输出 `marks` 段；`GET /v1/params/resolve` 的响应带 `svg` 字段。

**后果**：
- 前端画球场只有一条路径：拿 `svg` 段，按米转像素，不出现任何字面量。
- 标线与判定分离：`marks` 只影响绘制，`ThreePointSpec` 才影响分值，两者的测试也分开。
