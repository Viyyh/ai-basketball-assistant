# v1.1 范围说明

> 本文档是 **PRD v1.0 的增量**，不是替代。
> `PRD.md` 原文不改（它是"教练端采集工具"的完整定义，仍然有效）；本文档只做三件事：**补洞、加球员、缓功能**。
> 每条改动都注明依据，方便半年后回来看"当时为什么这么定"。

- 版本：v1.1
- 日期：2026-10-21
- 前提：单机位（场边高处一部手机）、教练单人操作、内测 ≤ 15 人

---

## 0. 一句话

**补掉四个会产出"看起来正常、其实错了"的数据的洞，并把"球员"从名单里的一个条目，变成一个有数据卡、能被比较的实体。**

**验收定义（v1.1 做完了是什么样）**

> 一位教练，用手机录一场 5v5，30 分钟内拿到一份报告：
> 我方/对方分栏；每个我方球员有出手分布图和命中率；每个数字点开能看到对应视频片段；没有数据的地方显示 `—` 而不是 `0`。

这就是"NBA2K 式分析"的**第一层地基**。评分、对比、雷达图都建在这句话之上——地基不牢，上面全是错的。

## 1. 三条原则

| # | 原则 | 含义 |
|---|---|---|
| P1 | **数字优先于界面** | 任何新页面上线前，先确认它背后有一个可信的数字。没有数字的页面 = 装饰。 |
| P2 | **宁可少标，不可标错** | 继承 PRD 3.3 / 9.2。低置信度显示"未识别"，不猜。 |

## 3. A 层 · 补洞

### A1 · 阵营归属

**问题**

PRD 的 `team_stats`（命中数、弧外命中、快攻、回合、失误）表达的是"我方"统计，但 `events` 里没有任何字段说明这次出手是谁的。单机位一帧里两队都在，AI 无从区分。结果是"我方三分 7/15"里混进了对手的出手，而报告看上去完全正常——正是 PRD 风险 7.4 那一类错误。

**做法**

不引入 AI 颜色聚类。**阵营由教练的补录动作确定**：

| 教练动作 | 结果 |
|---|---|
| 选了我方某个球员 | `team_side = OURS`，`player_id = 该球员` |
| 选了「不是我方」 | `team_side = OPPONENT`，`player_id = null` |
| 选了「看不清」 | `team_side = UNKNOWN`，`player_id = null` |
| 未补录 | `team_side = UNKNOWN`，`player_id = null` |

**为什么不做颜色聚类**：业余比赛球衣颜色不统一、有撞色、有深浅两套，颜色分类的误判率会在 20% 以上，而误判是**静默的**。教练补录时顺手点一下"不是我方"，成本几乎为零，准确率 100%。用零成本换 100% 准确，优于用复杂模型换 80%。

**报告变化**

- 球队数据页拆成「我方 / 对方」两栏，各自有出手数、命中数、命中率
- 未知阵营的事件单独计数，并写入 `warnings`：「本场 23 个事件未标注阵营，不计入任何一方」
- 补录进度分母 = 全部待补录事件（含对方），因为对方事件也要标"不是我方"才算处理完

**验收**

1. 报告 JSON 里能同时看到 `team_stats`（我方）与 `opponent_stats`（对方）
2. 未标注事件不进入任何一方的分子分母
3. 全部标"不是我方"时，我方命中数为 0 而不是空

---

### A2 · 进攻方向与半场镜像

**问题**

PRD 4.5 定义「x 轴 = 沿进攻方向，从篮筐指向中场」。但全场有**两个**篮筐，上下半场还要换边。契约里没有"这一节我方攻哪边"，于是热图会把两节的投篮画成两个镜像的簇，底角/翼侧/弧顶的分区统计全部错位。

**做法**

- 新建活动时多一个必选项：**上半场我方进攻方向**（左 / 右）。默认给"左"，但界面上必须一眼能看到并可改。
- `periods[]` 每节记录 `attacking_basket`（`LEFT` / `RIGHT` / `UNKNOWN`），由系统按"上下半场换边"规则推导，教练可单节覆盖。
- 报告页给一个**「翻转」开关**：只影响展示，不改写数据。教练发现镜像错了，一键翻过来，而不是重跑。

**验收**

1. 第二节的热图与第一节关于中线对称，而不是重叠在同一侧
2. 翻转开关切换后，数据库里的坐标不变
3. `attacking_basket = UNKNOWN` 时，热图显示"方向未确认"横幅，不画分区线

### A3 · 补事件 / 排除误检

**问题**

PRD 9.2 #2.5 要求投篮查全率 ≥ 85%，意味着**15% 的出手永远不会出现在报告里**，而教练没有任何手段补上。同样，AI 误判的"出手"（传球被识别成投篮、观众走动被识别成出手）也删不掉。

**做法**

事件页增加两个动作，与"归属"平级：

| 动作 | 交互 | 数据 |
|---|---|---|
| **补一次出手** | 在时间轴上点一个时刻 → 在球场图上报位置（可跳过位置）→ 保存 | 新建 event，`source = COACH`，`confidence = 1.0` |
| **这不是投篮** | 长按事件卡 → 「排除」 | `status = EXCLUDED`，数据保留，可撤销 |

`status = EXCLUDED` 的事件：

- 不计入任何统计
- 仍在 JSON 里，可追溯（不能物理删除，否则教练无法确认自己的操作生效了）
- 列表里默认隐藏，可切换显示

**验收**

1. 补录进度分母 = `status = ACTIVE` 的事件数
2. 排除 3 个事件后，报告里的出手数减少 3，且 `coverage.events_excluded = 3`
3. 撤销排除后数字恢复

### A4 · 从相册导入视频

**问题**

当前唯一的视频入口是 `camera` 组件连续录制 40 分钟（约 5 GB）。这条路在真机上完全没有验证过：切后台、发热、单文件大小限制、`stopRecord` 失败，任何一个环节出问题，内测一场都跑不了。

**做法**

- 首页在"开始新录制"下方增加次级入口：**「导入已有视频」**
- 调 `wx.chooseMedia`（`mediaType: ['video']`，单文件 ≤ 2 GB）
- 复用现有上传页；处理中与报告页完全不变
- 录制页保留，但定位从"唯一入口"降为"可选入口"

**验收**

1. 从相册选一段 2 分钟视频，能走完上传 → 处理 → 报告（接 mock 报告也算通过）
2. 导入的视频在历史列表里与录制的视频无差别

## 4. B 层 · 球员数据

### B1 · 号码即身份

**问题**

`player_id` 恒为 null，教练补录后事件有了归属，但**没有跨场聚合的主键**。球员卡要成立，先要保证"同一个人在不同场次里是同一个 id"。

**做法**

- 名单里 `number` 在球队内唯一（数据库唯一约束 + 前端校验）
- 补录写入 `player_id`（不是号码字符串，是 id）
- 球员卡按 `player_id` 聚合，`number` 只用于展示
- 球员可标记"已离队"（`status`），**不物理删除**——历史报告要保留

**验收**

1. 同一球员两场比赛的数据能合并
2. 两个球员用同一个号码时，前端拦下并提示

---

### B2 · 球员数据卡 v0

**内容**（每个数字都可点开 → 跳到对应事件列表）

| 区块 | 字段 | 数据来源 |
|---|---|---|
| 基本 | 出场节次、总出手、总命中、得分 | 补录后的事件 |
| 出手分布 | 出手位置点图 + 命中/未中着色 | `x_m / y_m / made` |
| 分区域 | 弧内 / 弧外 的出手数与命中率 | `judge()` 产出的 `behind_three_point_line` |
| 三分 | 弧外出手、弧外命中、弧外命中率 | 同上 |

**必须有的诚实提示**

- 出手数 < 20 时，显示「样本不足（N 次出手）」，**不给命中率排名**
- 任何缺数据的字段显示 `—`，不显示 `0`
- 卡片顶部常驻口径：赛制 + 年龄段 + 场次数

**验收**

1. 球员卡上的出手数，等于该球员在事件列表里筛选出的条数
2. 点击任一数字，能跳到筛选好的事件列表
3. 样本 5 次出手的球员，不显示"命中率 60% 全队第一"

### B3 · 评分 v0（分档，不做 0-99）

**为什么不做 0-99**：NBA2K 的分数是设计出来的，不是算出来的。一个自己算出来的 78 分，只要教练问一句"凭什么"，产品就崩了。**分档 + 样本量 + 一句话依据**，才扛得住追问。

**三个维度**（只做单机位能证明的）

| 维度 | 输入 | 说明 |
|---|---|---|
| 终结 | 弧内出手数、弧内命中率 | 篮下和中距离 |
| 远投 | 弧外出手数、弧外命中率 | 5v5 即三分；3x3 即远投 |
| 参与 | 个人出手 / 全队出手 | 反映进攻参与度，不评价好坏 |

**输出示例**

```
终结   B   （弧内 34 投 19 中，53%，样本充足）
远投   C   （弧外 12 投 3 中，25%，样本偏少）
参与   A   （占全队出手 28%）
```

**明确不做**：传球、防守、篮板、抢断评分——这些需要**逐人跟踪**，是 v2 的事。第一版给不了的东西，一个都不假装。

**规则版本化**：报告里写 `rating_rules: "v0"`。以后调阈值，历史数据能按旧规则回算，不会出现"上个月是 A、这个月变 B、数据没变"的情况。

**验收**

1. 每个分档都能展开看到输入数据
2. 样本不足时给"样本不足"而不是最低档
3. 同一份数据用同一版规则算两次，结果一致

---

### B4 · 数据完整度标注

- 所有聚合数字旁标「基于 N/M 场」
- 有场次未补录时，数字加虚线边框 + 提示「该场未补录完成，已按排除计」
- 球队数据页顶部一行：「本页数据基于 8 场，其中 3 场补录未完成」

**验收**：任取一个聚合数字，能说出它由哪几场、哪几个事件组成。

## 5. C 层 · v1.1 缓做（UI 保留，不接后端）

这些页面 F 轨已经画好了，**不删**，只是第一版不接真实数据：

| 功能 | 处理 |
|---|---|
| 战术板 / 新建战术 | 保留入口，显示「内测后开放」 |
| 对手列表 / 对手详情 | 保留入口，同上 |
| 套路演练报告 | 保留页面，模板可选，报告结构与比赛同构 |
| 实时分析 | 灰显占位（PRD 6.2 已定） |
| 分享 / 导出 PDF | 不做 |
| 3x3 完整规则（21 分制、洗球） | 不做，只做出手点与命中（PRD 6.3 已定） |

**理由**：这五块都不产出"球员数字"。在 B 层跑通之前做它们，等于给一个还没验证的核心加外壳。

## 6. 契约 v1.1 变更

| 位置 | 变更 | 理由 |
|---|---|---|
| `schema_version` | `1.0` → `1.1` | 破坏性变更需要升版本 |
| `events[].team_side` | **新增** `OURS / OPPONENT / UNKNOWN`，必填 | A1 |
| `events[].source` | **新增** `AI / COACH`，必填 | A3 |
| `events[].status` | **新增** `ACTIVE / EXCLUDED`，必填 | A3 |
| `periods[].attacking_basket` | **新增** `LEFT / RIGHT / UNKNOWN` | A2 |
| `opponent_stats` | **新增**，字段同 `team_stats` | A1 |
| `coverage` | **新增** `events_total / events_attributed / events_excluded / events_side_unknown` | A1 + A3 |
| `ratings` | **新增**，球员分档结果，含 `rating_rules` 版本号 | B3 |

`team_stats` 语义不变，仍是**我方**统计。

## 9. 风险
